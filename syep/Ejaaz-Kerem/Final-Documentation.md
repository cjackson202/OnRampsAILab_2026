## 1. Where This Started: AI & Agent Fundamentals (Week 2)

Before building anything, I spent Week 2 getting a working understanding of generative AI and where it fits inside Microsoft's product lineup, since I'd be building on top of it for the rest of the summer.

The short version of what I learned: a generative model doesn't look answers up, it predicts the next token in a sequence, one piece at a time, based on probability — which is also why the same prompt can produce a slightly different answer twice. Large Language Models are what make this possible, trained on enormous amounts of text so they can generate language that reads naturally. On their own, LLMs only know what they learned during training, which is frozen at a point in time and has no way of knowing anything current or private. Retrieval-Augmented Generation (RAG) fixes that: a user's question goes to an orchestrator, which queries a search index for relevant content, and that retrieved context gets added into the prompt before it's sent to the model. This turned out to be directly relevant to my own project — Draft Architecture and WAF Score both ended up grounded in real Azure documentation this way, not just the model's training knowledge.

The other concept that mattered most going in was agentic AI. A chatbot responds to a prompt and stops there. An agent is an LLM given instructions and access to tools, so it can reason through what needs to happen, act on that reasoning (often by calling a tool), and factor the result back into what it does next — a loop, not a single response. That loop is essentially what CSA Assistant does across its three skills: read something, reason about what's actually there, act (extract, draft, or score), and hand control back rather than assuming it should keep going on its own.

On the Microsoft side, I mapped out where different products sit: Microsoft Foundry for model/infrastructure-level work, the Microsoft Agent Framework for building agents in code, Copilot Studio for building a copilot with less code, and Azure AI for developers building directly on Azure OpenAI. I ended up building in Copilot Studio, which let me focus on the actual problem (extraction, drafting, scoring) instead of infrastructure.

## 2. The Problem (Week 3)

I came into this internship having spent most of my time in embedded systems and sensor fusion, where the core skill is noticing when something doesn't quite add up between what a system is doing and what it should be doing. I went looking for that same kind of gap, just in cloud instead of hardware, and found it in how Cloud Solution Architects (CSAs) run customer calls.

A CSA joins a live conversation to gather requirements for a proposed Azure architecture: workload type, scale, compliance needs, budget, existing stack. Customers correct themselves mid-call, add details later that contradict something said earlier, or mention constraints in passing that never get revisited. By the time the architect sits down to actually design the solution, some of that gets lost or misremembered — not because the architect isn't paying attention, but because tracking a live, shifting conversation and building a mental model of the requirements at the same time is hard to do perfectly every time.

There's a second piece that looks separate at first but comes from the same root cause. Once a CSA has a proposed architecture, they're expected to evaluate it against the Well-Architected Framework's five pillars. Doing that well and consistently isn't something most technical people can do out of the box — it comes from having sat through hundreds of calls and designs before, building an intuition for what a strong architecture looks like versus a weak one. A newer CSA hasn't built that intuition yet, so both what gets captured during the call and how the resulting design gets judged can vary a lot depending on experience.

Both problems come down to the same thing: a newer architect doesn't yet have the pattern recognition a senior one has built up over time.

**Target user:** a Cloud Solution Architect, especially someone early in their career who's still building the judgment to catch every important detail live and to score a design against WAF from memory. The secondary beneficiary is the customer — when less gets lost between the call and the design, they end up with a more accurate first-draft architecture.

**Solution concept:** an agent that sits alongside a CSA's customer call and turns the conversation directly into a scored first-draft architecture — taking a transcript as input, extracting structured requirements, drafting a first-pass architecture grounded in real Azure documentation, and scoring that architecture against the five WAF pillars, with a downloadable file at the end.

## 3. What I Built: CSA Assistant (Week 4–5)

CSA Assistant is a single Copilot Studio agent, running on Claude Sonnet, built around three chained skills plus a fourth capability layered on later: a downloadable first-draft Word document.

### 3.1 The three skills

**Extract Requirements** reads a customer call transcript and pulls out five categories: workload type, expected scale, compliance needs, budget sensitivity, and existing technology stack. The two rules that matter most here: if the customer restates a number mid-call (a correction), the skill uses only the most recent value and tags the line **[Corrected]**, showing both the original and corrected figure rather than quietly using the new one with no explanation. If a category is never discussed, it's tagged **[Gap]** and left as "Not discussed" — never inferred from context or industry norms. The skill also flags connections it noticed but wasn't explicitly told (like a budget figure that was walked back and never restated) as a question back to the architect, not a conclusion it draws on its own.

**Draft Architecture** takes those structured requirements and proposes a first-pass Azure design, reasoned through in four parts: the *given* (what the requirements actually state), the *required* (what a valid design needs to satisfy that), *known relations* (foundational Azure knowledge connecting a kind of need to a kind of service — weighed, not applied automatically), and the *composed solution* (checking every category against every other one, not five independently-justified answers sitting next to each other). It organizes output into Compute, Storage, Networking, Security/Identity, and Monitoring/Ops, names real alternatives it ruled out and why, and ends with three sections: **Design Tensions** (conflicts between two things the customer actually said), **Risks Noticed** (things the draft itself surfaces that nobody raised on the call, tagged **[Unverified Assumption]** or **[Gap]**), and **Open Items** (unresolved gaps carried forward from extraction).

**WAF Score** takes a draft architecture and scores each of the five Well-Architected Framework pillars — Reliability, Security, Cost Optimization, Operational Excellence, Performance Efficiency — on a four-level scale (Not Addressed / Emerging / Adequate / Strong) rather than a numeric score, since a single rough draft doesn't support that level of precision. Every justification is written as a named tradeoff ("the draft accepted the operational overhead of centralized secret rotation through Key Vault in exchange for meeting the stated PCI DSS key management requirement"), not a generic observation, and every rating is capped honestly whenever a real gap bears on it — whether that gap was flagged upstream or the skill notices it for the first time while scoring. It ends with a **Scoring Confidence** section listing every capped pillar and asking the architect directly whether they want to resolve those before treating the scorecard as final.

A router set of top-level instructions sits above all three skills, deciding which one to run and, critically, when to stop. Getting that stopping behavior right took a real bug fix: an early version had the agent silently run all three skills back to back the moment a transcript came in, including answering its own flagged question and proceeding as if it were resolved. The fix was reframing the opening instructions around three separate, deliberately-triggered stages, with an explicit rule that a flagged question has to be answered by the architect, not the agent itself.

### 3.2 Grounding it in real Azure documentation (RAG)

Draft Architecture and WAF Score are both grounded in real Azure documentation rather than the model's own training knowledge. This took a couple of wrong turns before landing on something that worked.

The first plan was to add Azure Learn pages as live **public website** knowledge sources. That turned out to be wrong for this specific set: Copilot Studio scopes a public-website source to a prefix capped at two path segments, and every relevant URL starts `learn.microsoft.com/en-us/azure/...` — `en-us` and `azure` already consume both allowed segments before reaching anything about Well-Architected or Architecture Center guidance specifically. The narrowest scope available would have covered the *entire* Azure docs corpus, not just the pages I actually wanted.

The fix was uploading curated **Documents** instead — PDF exports of the specific pages, attached at the agent level. 33 target URLs collapsed into 9 real files once exported (the entire Well-Architected Framework, all five pillars, principles, checklists, and tradeoffs, came down as a single `azure-well-architected.pdf`, since Microsoft Learn exports that whole depot as one file). Eight of the nine are Draft Architecture's material (compute/data-store decision trees, storage redundancy, Key Vault, hybrid connectivity, and so on); the ninth is WAF Score's. Each skill's instructions explicitly name which documents are "theirs" and note that the other skill's file is technically retrievable (everything's attached at the agent level) but out of scope for their own job.

A live-testing pass caught a second bug: citation markers in Draft Architecture's output didn't reliably track which retrieved source backed which specific sentence — confirmed via a citation tooltip showing a networking excerpt attached to an unrelated Entra ID RBAC claim. The fix was a per-citation self-check step added to both skills: re-verify each marker against its actual excerpt before finalizing, and drop any citation that doesn't genuinely support the sentence it's attached to, rather than leave a mismatched one in place. A claim with the wrong citation is worse than an uncited claim, since it looks verified when it isn't.

A third, smaller gap turned up during this week's live testing: a WAF Score run came back with only one citation (Security, referencing the Key Vault document) across all five pillars, even though the skill's own instructions call for grounding every pillar in the Well-Architected Framework document specifically. The likely cause — the skill's own instructions already summarize each pillar's core principles in a few bullet points, and combined with the model's general familiarity with WAF's public checklist codes (RE:06, SE:09, and so on), it had enough to answer confidently without actually issuing a search. The fix was tightening the instruction from "check it and cite" to something closer to a requirement: search the source *before* writing each pillar's justification, even when the checklist items are ones the model already recognizes, and only skip the citation if a real search genuinely comes back empty. That fix is republished; a follow-up test to confirm all five pillars now cite real excerpts is still on my list.

### 3.3 The downloadable draft package

The last capability — a downloadable, formatted Word document at the end of a conversation — took the most engineering, mostly because of a real platform limitation I had to work around mid-build.

**Original plan:** a Copilot Studio "Document Output" prompt (fills a Word template from AI-generated field values) called from inside a classic Power Automate cloud flow, wired into the agent as a callable tool. I built and fully tested this flow — trigger, prompt, file creation, sharing link, response back to the agent — and it worked standalone. The problem was attaching it: classic flows have to live inside a Dataverse Solution alongside the agent to be discoverable in Copilot Studio's "Add a tool → Workflows" picker, and even after creating the solution, adding the flow, and adding the agent itself (all 35 of its components) into that same solution and republishing, the flow never showed up in the tool picker. I traced this to a genuine, unresolved Microsoft product bug — a live Microsoft Q&A thread from around the same time, with a Microsoft moderator confirming they'd reproduced it, plus Microsoft's own documentation showing the native Workflows "Agent" node (successor to "Prompt") has no Document output type at all, meaning the underlying feature the classic flow depended on isn't even reachable from the new experience.

Given the choice between continuing to troubleshoot a confirmed platform bug, using a manual workaround, or rebuilding the same functionality natively, I chose to rebuild. The native version replaces the Document Output prompt with **Populate a Microsoft Word Template** (a Word Online connector action) using real Word Content Controls, since that connector works fine as a plain connector-type action inside native workflows. The catch: Content Controls have to be inserted into the actual `.docx` file as OOXML Structured Document Tags, and doing that by hand for the 33 fields the template needed wasn't practical. I built the template programmatically instead — a Node.js script (using the `docx` package) generated the base document with `{{FieldName}}` placeholder text in the right structure, then a Python post-processing script scanned the generated XML and wrapped each placeholder in a real Plain Text Content Control SDT, tagged with the matching field name. (One regex bug along the way — an ungreedy match without a run-boundary exclusion backtracked across multiple XML runs and corrupted the document; fixed with a tempered-greedy-token pattern, then re-verified via XML parsing, a `python-docx` load, and a rendered PDF visual check.)

The final native workflow: an **Agent** node extracts 33 flat fields from the three skills' combined output (`SourceContent`) → **Populate a Microsoft Word Template** fills the content-controlled template → **Create file** persists it → **Create sharing link** generates a link → **Respond to the agent** returns the `DocumentURL`. This is what's attached to CSA Assistant today as the **Document Generator** tool.

One design decision changed mid-build at my own request: originally, generating the draft was going to fire automatically the instant WAF Score finished. I changed that, since an architect might still want to revise the requirements, tweak the architecture, or ask for a rescore before treating anything as final — the flow shouldn't run just because scoring happened to complete. Instead, the agent's own Instructions now tell it to end its WAF Score reply with a plain-text offer ("Would you like me to generate the downloadable draft package now, or is there something you'd like to revise first?") and wait for the architect to actually say yes, while also honoring a request for the draft at any later point in the conversation, independent of that offer. Because CSA Assistant is built in Copilot Studio's newer "Instructions box" experience rather than the classic Topics canvas, there's no Question node or Condition node to build this with — it's entirely a paragraph of natural-language instruction that the underlying model reasons over each turn, re-reading its own earlier skill outputs from the conversation rather than relying on any explicitly-set variable.

One small housekeeping note worth mentioning here: once the native workflow was tested and working, I deleted the now-unused classic "CSA Document Generator" flow rather than leaving two versions of the same capability sitting around.

## 4. Testing the Agent

### 4.1 First test pass (Week 4)

The first real test used a fake customer call transcript with a few tricky things built in on purpose: a mid-call correction, a budget offered and then walked back with no replacement number, a PCI DSS compliance requirement, and no mention at all of monitoring or operations.

Extract Requirements used the corrected 100,000-user figure rather than the original 10,000, tagged it as a correction, and — this was the result I cared about most — refused to guess a number when the budget was walked back with nothing to replace it, marking it "to be determined" instead of defaulting to the only real figure it had. It also correctly recognized the existing SQL Server database wasn't in scope for the migration, since the customer said that piece wasn't moving.

Draft Architecture organized the response into the five categories, correctly left storage unaddressed rather than defaulting to an Azure database the customer never asked for, and — since the budget was unresolved — presented two options side by side instead of guessing which one the customer would actually want. It also caught something nobody raised on the call: the app would run in Azure, but every request still had to reach an on-prem database with no stated failover posture. That's exactly the kind of thing the "Risks Noticed" section exists for, and finding it during this test run is actually what prompted me to split "Design Tensions" (conflicts between two things the customer said) and "Risks Noticed" (risks the draft itself surfaces) into two separate categories in the instructions, since the first version of the skill was lumping them together.

WAF Score lowered several pillars, but was explicit that it was doing so because of missing information (no confirmed budget, no stated uptime requirement), not because the design itself was bad — a distinction that mattered to me, since I didn't want a rough first draft being penalized for the incompleteness of the source call rather than an actual design flaw.

Copilot Studio's built-in auto-generated test tool scored the agent 64% (7/11). Looking at the four failures individually, all of them were cases where the test tool asked the agent to score or draft something with nothing actually attached, and in every case the agent correctly said it didn't have enough to go on and asked for the missing piece rather than making something up — which is exactly the behavior I wanted. The automatic grading tool seems built to reward answering immediately and confidently, and doesn't appear to know how to judge an agent that's supposed to pause and ask questions instead. That mismatch, not an actual agent problem, is what the 64% was really measuring.

### 4.2 Second test pass — live, end to end (Week 5, this week)

This week's testing ran the full pipeline live in Copilot Studio's Preview chat, start to finish, using a shorter internal-analytics-dashboard scenario (200 daily users, PostgreSQL backend, tight $2,000/month budget, part-time engineering team, no compliance requirement).

Every stage stopped correctly and asked before continuing, rather than assuming: Extract Requirements flagged that the transcript never specified where the PostgreSQL database was actually hosted and asked whether to resolve that before drafting; Draft Architecture built a full cost-sized proposal (~$143–148/month against the $2,000 ceiling, about 7% of budget) and again asked before moving to scoring rather than assuming the architect was satisfied; WAF Score produced a full five-pillar table with tradeoff-framed justifications, capped three pillars with a specific, named reason for each, and ended with the new offer behavior exactly as designed: *"Happy to revise the draft to close either before we treat the scorecard as final — or if you're satisfied with the current state, I can generate the downloadable package now. What would you like to do?"* — no automatic firing, a genuine choice.

Saying yes triggered the Document Generator tool correctly, and it returned a real, working SharePoint link to a fully populated Word document — verified field by field: workload name and a deliberately blank "Prepared:" date line (left blank on purpose, since the model has no reliable way to know today's actual date and guessing produced a wrong one in early testing), the full Requirements Summary section with **[Corrected]** tags preserved exactly, and the WAF scorecard table with all five pillars populated. The closing message also correctly pulled the actual open items from that specific run into its reminder text (PostgreSQL location unresolved, database credential privilege level unspecified, no CI/CD pipeline) rather than a generic disclaimer.

The one real gap this pass surfaced was the missing WAF Score citations described in section 3.2 above — caught specifically because I was checking the citations shown in the live chat panel, not just trusting the output looked complete.

## 5. Lessons Learned

**Start with the user's actual workflow, not the tool's default behavior.** The single biggest design change this project went through — splitting the draft-package generation from an automatic action into an explicit offer-or-request — came directly from thinking about how a CSA actually works a call: they don't finish scoring and immediately want a final PDF, they usually want to revise something first. The technically simpler choice (auto-generate on WAF Score completion) would have shipped a worse product.

**"It answered confidently" and "it answered correctly" are different things, and it's worth building instructions that let an agent tell the difference.** Nearly every meaningful fix this summer — the recency/correction tagging in Extract Requirements, the [Gap]/[Unverified Assumption] distinction in Draft Architecture, the honest-capping rule in WAF Score, the per-citation self-check — was really the same principle applied in a different place: don't let the agent paper over what it doesn't actually know. The automatic test tool scoring 64% while the agent was behaving exactly as intended is the clearest example of why that principle has to be checked by reading actual output, not just a pass/fail score.

**Platform bugs are a real part of building on a preview/evolving product, and the fix is usually "understand the constraint, then design around it," not "wait for it to get fixed."** The classic-flow tool-picker bug cost real time to diagnose, but rebuilding as a native workflow — including generating Word Content Controls programmatically since there was no practical way to insert 33 of them by hand — ended up being a better-architected solution than the original plan, not just a workaround.

**Grounding a model in real documentation is not a one-time setup step.** Getting RAG right took three separate passes: realizing public-website scoping wouldn't work for this document set, catching a citation-tracking bug where a marker didn't match its actual source, and catching a case where the model skipped searching altogether because its own instructions already summarized enough to sound confident. Each of those required actually reading the generated output and its citations closely, not just checking that an answer was produced.

**Communication matters as much as the technical build.** Presenting this project to FTEs, and explaining tradeoffs like "why does the document leave the date blank" or "why doesn't this fire automatically" to a non-technical audience, took as much thought as building the underlying agent.

## 6. Where Things Stand

CSA Assistant currently does everything the original solution concept called for: it turns a call transcript into structured, tagged requirements; drafts a first-pass Azure architecture grounded in real documentation with named tradeoffs and flagged risks; scores that draft against all five Well-Architected Framework pillars with honest, capped ratings; and, on request, generates a downloadable, properly formatted Word document of the whole package. All of it has been tested live, end to end, including the platform-bug-driven rebuild of the document-generation path.

Two small items are still open rather than fully closed: confirming the WAF Score citation fix produces real citations across all five pillars (not just Security) in a fresh test run, and running a couple more edge-case tests beyond the two full pipeline runs done so far — particularly around what happens when an architect asks for the draft package mid-conversation, out of the blue, rather than right when it's offered.
